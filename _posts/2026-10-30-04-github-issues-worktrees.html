Un coding agent è molto più utile quando lavora su richieste delimitate, visibili e verificabili. Il video propone di usare GitHub come centro operativo: un'issue descrive il lavoro, un branch lo isola, una pull request lo sottopone a verifica.

Nel video: 16:17–22:04.

1. Un'issue al posto di un prompt dimenticato

L'issue non deve limitarsi a «aggiungi la funzionalità X». Deve raccontare il problema, definire il comportamento atteso e stabilire come verificare il risultato. Questo la rende utile sia per una persona sia per un agente.

Esempio di GitHub Issue

Titolo: Aggiungere il filtro per stato alla lista delle attività.

Contesto: oggi la pagina mostra tutte le attività senza distinzione.

Requisiti: filtri «Tutte / Aperte / Completate»; filtro persistente nell'URL; nessuna regressione nella modifica delle attività.

Accettazione: i tre filtri mostrano le righe corrette; il refresh conserva la selezione; i test esistenti passano.

Fuori ambito: nessun cambiamento a ruoli e autorizzazioni.

Nel video il relatore mostra come l'issue possa anche contenere commenti, screenshot, evidenze dei test e richieste di chiarimento: diventa la traccia dell'intervento.

2. Branch e worktree: due concetti diversi

Un branch identifica una linea di sviluppo nel repository Git. Un worktree è una directory di lavoro associata a un determinato branch o commit dello stesso repository. Con più worktree puoi aprire sessioni separate di agenti senza obbligarli a modificare gli stessi file nella stessa directory.

fix/login
Agente B
Pull request + test → merge controllato

Una procedura locale di esempio:

git fetch origin
git worktree add -b feature/filtro-stato ../app-filtro origin/main
git worktree list

Questi comandi creano un branch e una nuova directory da origin/main. Non pubblicano il lavoro da soli: serviranno commit, push e pull request. Non usare automaticamente questi comandi in una cartella con modifiche non salvate senza averne controllato lo stato.

3. Il flusso completo per una modifica

  1. Definisci l'issue: problema, requisiti, vincoli, test attesi.
  2. Assegna il lavoro: l'agente legge issue, codice e regole del progetto.
  3. Isola la modifica: usa un feature branch; aggiungi un worktree se serve parallelismo reale.
  4. Implementa e documenta: l'agente può aggiornare l'issue con motivazioni ed evidenze.
  5. Apri la PR: riepilogo dei file toccati, verifica e limitazioni note.
  6. Rivedi e integra: i controlli automatici passano, una persona approva, poi si effettua il merge.

4. Quando evitare il parallelismo

Se due agenti devono modificare gli stessi componenti, migrazioni o contratti API, aumentano i conflitti e il lavoro di integrazione. Prima di lanciare più sessioni, chiediti se le issue siano davvero indipendenti. Gli worktree isolano i file di lavoro, non database condivisi, servizi cloud, segreti e ambienti di produzione.

5. Esercizio operativo

  1. Apri due issue con criteri di accettazione concreti.
  2. Fai implementare la prima su un branch dedicato.
  3. Chiedi una PR con riepilogo, test eseguiti e rischi residui.
  4. Prova un worktree soltanto per una seconda modifica indipendente.
  5. Verifica quali passaggi sono tracciati in GitHub e quali no.
Risultato atteso

Il lavoro dell'agente diventa leggibile e revisionabile: dalla richiesta iniziale al merge, senza modifiche dirette e opache alla versione stabile.
