Il software generato dall'AI può funzionare nella demo e rompersi alla prima modifica. Per questo il video richiama un principio classico dell'ingegneria del software: non è il modello a decidere se il codice è pronto, sono le verifiche.

Nel video: 22:04–26:30.

1. Il problema delle regressioni

Quando un agente corregge un bug, potrebbe introdurre un errore in una funzionalità che prima funzionava. I test automatizzati cercano proprio questo genere di regressioni. Il relatore distingue test unitari e test end-to-end, da eseguire automaticamente sulle pull request.

ControlloChe cosa verificaQuando eseguirlo
Lint e formattazioneConvenzioni e problemi statici sempliciOgni PR
Test unitariFunzioni e componenti isolatiOgni PR
Test di integrazioneInterazioni tra API, servizi e datiOgni PR o nelle pipeline dedicate
Test E2EPercorsi reali dell'utentePR rilevanti e/o rilascio
Dependency e secret scanningLibrerie vulnerabili e possibili credenzialiContinuamente e a ogni cambio
Review tecnica e sicurezzaDesign, autorizzazioni, rischi non coperti dai testPrima del merge

2. Un esempio minimo di GitHub Actions

Per un progetto JavaScript con script test e build definiti in package.json, si può partire da questo workflow. È un modello da adattare, non una configurazione universale.

name: CI
on:
  pull_request:
  push:
    branches: [main]

jobs:
  verify:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '22'
          cache: npm
      - run: npm ci
      - run: npm test -- --run
      - run: npm run build

Il comando di test dipende dal runner scelto: se il progetto non usa Vitest o non dispone di quegli script, va sostituito. Per repository con frontend e backend separati si possono creare job distinti, eventualmente con matrix e servizi di test.

In produzione è opportuno valutare anche il pinning delle GitHub Actions a revisioni affidabili, permessi minimi del token e protezione dei segreti.

3. Bloccare i merge che falliscono

Il video mostra come i check associati alla pull request possano impedire di integrare una modifica difettosa. In GitHub questo richiede la corretta configurazione di ruleset o protezioni del branch, non semplicemente la presenza di un file YAML. Un controllo facoltativo che fallisce ma viene ignorato non costituisce una barriera affidabile.

4. Review AI: utile, ma non sufficiente

L'autore propone sessioni separate di revisione del codice e di sicurezza, eventualmente usando un provider diverso da quello che ha scritto la modifica. L'approccio può identificare bug, problemi di chiarezza e vulnerabilità evidenti.

Tuttavia nessuna review AI garantisce la sicurezza dell'applicazione. Per funzioni sensibili servono controlli sull'autorizzazione, test, strumenti specializzati e, quando necessario, un audit umano. L'OWASP Top 10 è un buon riferimento, non una checklist che da sola certifica la sicurezza.

5. Tre prompt di verifica

Code review

Analizza il diff rispetto a main. Elenca soltanto problemi concreti, con file, riga, scenario di riproduzione e gravità. Non inventare esecuzioni di test.

Security review

Esamina autenticazione, autorizzazioni, validazione input, gestione dei segreti, dipendenze e accessi ai dati. Se non puoi dimostrare una vulnerabilità, descrivila come ipotesi da testare.

Test gap review

Confronta i criteri di accettazione dell'issue con i test esistenti. Identifica percorsi non coperti e proponi test deterministici.

6. Esercizio operativo

  1. Individua tre funzioni critiche e aggiungi test che fallirebbero in caso di regressione.
  2. Configura GitHub Actions su una pull request di prova.
  3. Attiva le protezioni del branch per i check più importanti.
  4. Chiedi una review AI indipendente; verifica manualmente i rilievi.
  5. Documenta i risultati nella PR, compresi i test non effettuati.
Risultato atteso

Una modifica AI non arriva su main soltanto perché «sembra funzionare»: deve superare criteri tecnici espliciti e una decisione di rilascio.
